# Deliverable 5: Reflection Sheet

## 1. In a business setting, what clarifying questions would you ask when assigned this project?

Before writing code I would ask about scope and data: which topics are in the approved knowledge base, who owns that content, and how often it changes, because grounding is only as good as its source. I would ask for the escalation policy in writing (which categories always go to a human, and the expected response time), and what the agent is forbidden to say, such as timelines, guarantees, or compliance reasoning. I would ask about volume and channels: how many conversations per day, voice only or voice and chat, and expected languages. I would ask about integrations: is there a real ticketing system and CRM to write into, or should records land in a database for now. Finally, I would ask how success will be measured (deflection rate, escalation quality, customer satisfaction), and who is accountable when the agent hands a case to a human, because a handover with no owner is worse than no handover.

## 2. What was the most significant challenge you faced while building this, and what was its root cause?

The most significant challenge was making the voice channel reliable end to end, because text mode worked while the same conversation over voice failed in ways text testing could not reveal. The root cause was that every layer between the human mouth and the database rewrites the message: speech-to-text renders "TXN-9001" as "TXN nine thousand and 1", the deterministic templates rendered database literals like "2400 USD" that the text-to-speech voice reads digit by digit, and even the hyphen in the reference was spoken as "minus". The deeper root cause was testing the pipeline only at the text layer. The fix was to treat speech as a first-class channel: normalize spoken references into canonical IDs on input, format responses for speech on output, and keep the canonical text in the audit trail. The lesson for the business is that voice agents need channel-specific acceptance tests, not just API tests.

## 3. If you were to start this project again with your current knowledge, what is the one thing you would do differently to make the solution more robust or efficient?

I would define the Store interface and its two implementations (Supabase and a deterministic file-backed mock) on day one, before any agent logic, and I would write the concurrency contract down explicitly. I arrived at that design halfway through and it paid off immediately (tests, evaluation, and credential-free demos all run on the mock provider while production runs on Supabase), but earlier commits had drifted toward ad-hoc data access that had to be rewritten. The concrete robustness gap it would have prevented: my concurrency edge-case test found that parallel turns could tear the mock store's JSON file because writes were not atomic across the server and MCP subprocesses. Designing the storage contract first, with atomicity and idempotency as stated requirements rather than discoveries, would have surfaced that before it ever failed.

## 4. What edge cases did you account for, and how did you account for them?

Unsupported or out-of-scope questions: retrieval scores below a calibrated relevance threshold and the agent declines explicitly instead of guessing; greetings and "can you hear me?" get a short introduction instead, and rule-override attempts or requests for personal data are refused before any tool runs. Unknown references and customers: lookups return found false, and the agent says it could not find the record and offers a ticket rather than inventing a status. A reference it cannot read is never replaced by an older one from the conversation: it asks the customer to repeat it. Empty or malformed input: the text API rejects empty messages, and the voice webhook answers any missing transcript, unknown tool name, or bad arguments with a safe "I did not catch that" reply. AI failure: if the Claude runner errors or returns empty output, the deterministic responder takes over, so the customer never sees a stack trace. Duplicate requests: tickets and escalations deduplicate per conversation and category, and a repeat escalation enriches contact details instead of filing again. Incomplete escalation contact details: the agent collects them across turns until it has both a name and a valid email, validates the callback time, and never files a contact-less record. Store outages: tool failures produce an explicit error answer with an uncertainty note, never a fabricated result. Concurrency: parallel turns were failing against the mock store, so writes are now atomic (temp file plus rename) behind a cross-process lock, verified by a test that runs four conversations in parallel. Live voice testing also surfaced a whole class of input-shape edge cases: speech-to-text writes spoken emails without the @ symbol, spells reference prefixes letter by letter, and appends courtesy words like "for me" that broke strict parsing. One of the hardest bugs was mine rather than speech-to-text's: the webhook read the call ID from the wrong payload location, silently starting a new conversation for every utterance, which fragmented every multi-turn flow while single-turn answers still looked correct. Each of these now has a regression test. A final end-to-end audit before submission caught the rest — an activity panel that reported "no tool calls" because it read a 401 as empty data, MCP subprocesses that were never released, and secrets passed on a command line — and each fix is pinned by a test as well.

## 5. Which Claude model did you use and why? Name the alternative you considered, and explain how you weighed quality, cost, latency, and task complexity.

I used claude-sonnet-4-5 for both model roles: the backend Claude Agent SDK runner (default `CLAUDE_MODEL`, which words every reply) and the Vapi voice router (configured with the dated ID claude-sonnet-4-5-20250929, which only forwards the caller's words to the backend). The task is not raw generation, it is constrained phrasing: the decision engine has already picked the action and the tools have already returned the data, so the model only rewrites a known-safe template into natural language without adding claims. Sonnet sits at the point where quality is more than sufficient for that job while cost and latency stay reasonable for a real-time voice call, where every second of model latency is silence for the caller. The alternative I considered was Opus (the largest tier): higher quality on open-ended reasoning, but meaningfully more expensive and slower, and the extra reasoning depth is wasted on a prompt whose answer space is a short customer-safe sentence. I also weighed Haiku for latency and cost, but I judged the risk of sloppier adherence to the no-fabrication constraints too high for a regulated-adjacent payments context. A decisive practical factor: the whole pipeline is designed so that if the model is unavailable or misbehaves, the deterministic responder produces the same decision with template phrasing, which bounds the blast radius of any model choice.
